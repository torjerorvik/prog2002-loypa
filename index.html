Forelesningen

The lecture

Kompilering og linking

Hver .cpp-fil oversettes for seg til en objektfil – det er kompilering. Deretter setter linkeren sammen alle objektfilene og bibliotekene til én .exe. Feil i én fil gir kompileringsfeil med linjenummer. Feil som «unresolved external symbol» er linkerfeil: noe er deklarert, men linkeren finner ikke koden – som regel et bibliotek eller en .cpp som ikke er med i byggingen.

CMake

CMake er en oppskrift på byggingen som ikke er knyttet til én editor eller ett operativsystem. På Windows lager den en Visual Studio-løsning, på Linux lager den Makefiles. Du skriver oppskriften én gang i CMakeLists.txt, og den virker overalt. Det er to steg: konfigurere (CMake leser oppskriften og lager byggefiler i build/) og bygge (kompilatoren gjør jobben).

Innstillingene øverst i rot-CMakeLists.txt er cache-variabler. CMake husker dem i build/, så hvis du endrer dem i fila etter at du har konfigurert, må du slette build/ og konfigurere på nytt.

Submoduler

Bibliotekene i external/ (GLFW, glm, glad, stb, tinyobjloader) er ikke kopiert inn i repoet ditt. De er submoduler: pekere til en bestemt versjon i et annet git-repo. Derfor må du klone med --recursive, ellers får du tomme mapper.

CI – pipelinen

Hver gang du pusher, bygger GitLab prosjektet på en nøytral Linux-maskin. Grønn betyr «bygger der». Det er den byggingen som brukes ved vurderingen, så hvis det virker hos deg, men er rødt i pipelinen, er det pipelinen som har rett. Les loggen.

Compiling and linking

Each .cpp file is translated on its own into an object file – that is compiling. Then the linker joins all object files and libraries into one .exe. A mistake in one file gives a compile error with a line number. Errors like «unresolved external symbol» are linker errors: something is declared, but the linker cannot find the code – usually a library or a .cpp that is not part of the build.

CMake

CMake is a recipe for the build that is not tied to one editor or operating system. On Windows it generates a Visual Studio solution, on Linux it generates Makefiles. You write the recipe once in CMakeLists.txt, and it works everywhere. There are two steps: configure (CMake reads the recipe and writes build files into build/) and build (the compiler does the work).

The settings at the top of the root CMakeLists.txt are cache variables. CMake remembers them in build/, so if you change them in the file after configuring, you must delete build/ and configure again.

Submodules

The libraries in external/ (GLFW, glm, glad, stb, tinyobjloader) are not copied into your repository. They are submodules: pointers to a specific version in another git repository. That is why you must clone with --recursive, or you get empty folders.

CI – the pipeline

Every time you push, GitLab builds the project on a neutral Linux machine. Green means «builds there». That build is the one used for grading, so if it works for you but is red in the pipeline, the pipeline is right. Read the log.

Forelesningen

The lecture

Hvem gjør hva

OpenGL er ikke et vanlig bibliotek med kode i. Det er en spesifikasjon – en avtale om hvilke funksjoner som finnes – og det er skjermkortdriveren som faktisk gjør jobben. GLFW er biblioteket som snakker med Windows (eller Linux, eller macOS): det lager vinduet, gir deg en OpenGL-kontekst og leser tastatur og mus. GLAD henter OpenGL-funksjonene fra driveren.

Konteksten

En OpenGL-kontekst er all tilstanden OpenGL har for vinduet ditt: alle buffere, shadere og innstillinger lever i den. Den lages sammen med vinduet og må gjøres gjeldende (current) før du kan bruke den. Tenk på den som et arbeidsbord: du kan ikke legge noe på bordet før det står der.

Hvorfor GLAD trengs

De moderne OpenGL-funksjonene finnes ikke når programmet linkes. Adressene deres må slås opp i driveren mens programmet kjører, og det går først når det finnes en gjeldende kontekst. Det er GLAD sin jobb. Før GLAD har lastet funksjonene, er de bare tomme pekere – kaller du en av dem, krasjer programmet.

Versjonen

Før vinduet lages, forteller du GLFW hvilken OpenGL-versjon du vil ha og at du vil ha core profile (bare den moderne delen av OpenGL). Det gjøres med window hints. Versjonen bør stemme med det loaderen er generert for (PROG2002_GLAD_API, 4.6 på Windows). Eksemplene ber om 4.1, som er kursets minimum og fungerer overalt.

Render-loopen og dobbel buffering

Et grafikkprogram tegner hele bildet på nytt mange ganger i sekundet. Hver runde er én frame: tøm, tegn, bytt buffere, behandle hendelser. Du tegner aldri rett på skjermen. Du tegner på en bakside mens skjermen viser forsiden, og når bildet er ferdig, bytter du dem. Ellers ville brukeren sett halvferdige bilder som flimrer.

Å behandle hendelser (poll events) er det som lar vinduet reagere – på taster, mus og lukkeknappen. Glemmer du det, tror Windows at programmet har hengt seg.

Who does what

OpenGL is not an ordinary library with code in it. It is a specification – an agreement about which functions exist – and the graphics driver does the actual work. GLFW is the library that talks to Windows (or Linux, or macOS): it creates the window, gives you an OpenGL context, and reads keyboard and mouse. GLAD fetches the OpenGL functions from the driver.

The context

An OpenGL context is all the state OpenGL keeps for your window: every buffer, shader and setting lives in it. It is created together with the window and must be made current before you can use it. Think of it as a workbench: you cannot put anything on the bench before it is there.

Why GLAD is needed

The modern OpenGL functions do not exist when the program is linked. Their addresses must be looked up in the driver while the program runs, and that only works once there is a current context. That is GLAD's job. Before GLAD has loaded the functions they are just empty pointers – call one and the program crashes.

The version

Before the window is created, you tell GLFW which OpenGL version you want and that you want the core profile (only the modern part of OpenGL). That is done with window hints. The version should match what the loader was generated for (PROG2002_GLAD_API, 4.6 on Windows). The examples ask for 4.1, which is the course minimum and works everywhere.

The render loop and double buffering

A graphics program redraws the whole image many times a second. Each round is one frame: clear, draw, swap buffers, process events. You never draw straight to the screen. You draw on a back buffer while the screen shows the front buffer, and when the image is finished, you swap them. Otherwise the user would see half-finished, flickering images.

Processing events (polling) is what lets the window react – to keys, mouse and the close button. Forget it, and Windows thinks the program has hung.

    Koordinatene: NDC

    Det vertex shaderen leverer, er i normaliserte enhetskoordinater (NDC): x og y går fra −1 til 1, med (0, 0) midt i vinduet og y oppover. Det som havner utenfor, klippes bort. NDC bryr seg ikke om hvor stort vinduet er – derfor ser et kvadrat i NDC ut som et rektangel i et bredt vindu. Det fikser du senere med en projeksjonsmatrise.

    VBO – bytes på skjermkortet

    En vertex buffer object er en bit minne på skjermkortet. Du kopierer hjørnedataene dine dit én gang. Bufferen selv vet ingenting om hva bytene betyr – det er bare bytes.

    VAO – oppskriften

    En vertex array object beskriver hvordan bytene skal leses: «attributt 0 er to tall av typen float, starter ved byte 0, og neste hjørne kommer så mange bytes senere». Den husker også hvilken buffer dataene ligger i. Når du tegner, binder du VAO-en, og skjermkortet vet alt det trenger.

    Stride og offset

    Har hvert hjørne både posisjon og farge, ligger de ofte etter hverandre: posisjon, farge, posisjon, farge … (interleaved). Stride er hvor mange bytes ett helt hjørne tar. Offset er hvor i hjørnet et attributt begynner. Feil her er den vanligste årsaken til rare, forskjøvne trekanter.

    Shadere

    Shadere er små programmer i språket GLSL som kjører på skjermkortet. De kompileres mens programmet ditt kjører, og en feil i en shader gir ingen melding av seg selv – du må hente ut kompileringsloggen og skrive den ut. Vertex shaderen og fragment shaderen lenkes sammen til ett shaderprogram.

    Interpolasjon

    Gir du hvert hjørne en farge, blir fargen glidende blandet over trekanten: piksler nær det røde hjørnet blir mest røde. Det er rasteriseringen som gjør blandingen, før fragment shaderen får verdien. Se det i lekeplassen under.

    Indeksbuffer

    Et kvadrat er to trekanter, altså seks hjørner – men to av dem er de samme. Med en indeksbuffer lagrer du de fire unike hjørnene én gang og sier med tall hvilke tre som utgjør hver trekant. Det sparer minne, og i et sjakkbrett med 64 ruter merkes det.

    OpenGL er en tilstandsmaskin

    Å binde noe betyr «gjør dette til det gjeldende». De neste kallene virker på det som er bundet akkurat nå. Mange feil kommer av at noe annet enn du tror er bundet.

    The coordinates: NDC

    What the vertex shader delivers is in normalised device coordinates (NDC): x and y run from −1 to 1, with (0, 0) in the middle of the window and y pointing up. Anything outside is clipped away. NDC does not care how big the window is – which is why a square in NDC looks like a rectangle in a wide window. You fix that later with a projection matrix.

    VBO – bytes on the graphics card

    A vertex buffer object is a piece of memory on the graphics card. You copy your vertex data there once. The buffer itself knows nothing about what the bytes mean – they are just bytes.

    VAO – the recipe

    A vertex array object describes how the bytes are to be read: «attribute 0 is two floats, starts at byte 0, and the next corner comes this many bytes later». It also remembers which buffer the data lives in. When you draw, you bind the VAO, and the graphics card knows everything it needs.

    Stride and offset

    If each corner has both a position and a colour, they are often stored one after the other: position, colour, position, colour … (interleaved). Stride is how many bytes one whole corner takes. Offset is where in the corner an attribute starts. Mistakes here are the most common cause of strange, shifted triangles.

    Shaders

    Shaders are small programs in the GLSL language that run on the graphics card. They are compiled while your program runs, and an error in a shader gives no message by itself – you have to fetch the compile log and print it. The vertex shader and fragment shader are linked together into one shader program.

    Interpolation

    If you give each corner a colour, the colour is smoothly blended across the triangle: pixels near the red corner come out mostly red. Rasterisation does the blending before the fragment shader receives the value. See it in the playground below.

    Index buffer

    A square is two triangles, so six corners – but two of them are the same. With an index buffer you store the four unique corners once and say with numbers which three make up each triangle. It saves memory, and on a chessboard with 64 squares you notice.

    OpenGL is a state machine

    To bind something means «make this the current one». The next calls act on whatever is bound right now. Many bugs come from something else being bound than you think.

    Hva er forskjellen på en VBO og en VAO, i én setning hver?

    Hvor mange ganger kjører vertex shaderen og fragment shaderen for én trekant som dekker 5000 piksler?

    Hvordan får du vite at en shader ikke kompilerte?

    Bare ved å spørre: hent kompileringsstatusen og loggen etter kompilering (og lenkestatusen etter lenking) og skriv dem ut. OpenGL sier ingenting av seg selv.

    VBO: the bytes on the graphics card. VAO: the description of how to read the bytes, and which buffer they are in.

    How do you find out that a shader did not compile?

    Only by asking: fetch the compile status and log after compiling (and the link status after linking) and print them. OpenGL says nothing by itself.

    When does an index buffer pay off, and when does it not?

    It pays off when corners are shared between triangles – grids, squares, cubes. For a single triangle it gains nothing.

    Forelesningen

    The lecture

    Samme bilde, ny eier

    I disse fem issuene lærer du ingen ny grafikk. Du pakker kallene du skrev i #3 inn i klasser, slik at labben bare bruker dem. Det heter refaktorering: koden endres, oppførselen gjør det ikke. Testen etter hvert issue er derfor enkel: ser bildet helt likt ut som før?

    Et statisk bibliotek

    I #4 blir framework/ et statisk bibliotek: en samling ferdig kompilert kode som limes rett inn i hvert program som bruker den. Labbene og spillet lenker mot det. Når CMake-oppskriften sier at bibliotekets mappe og avhengigheter er PUBLIC, arver alle som lenker mot biblioteket dem automatisk – derfor finner labben VertexBuffer.h uten at du sier hvor den ligger.

    Header og kildefil

    Hver klasse har en .h-fil som deklarerer hva klassen kan (lovnaden) og en .cpp-fil som definerer hvordan (innfrielsen). Andre filer inkluderer bare headeren. #pragma once hindrer at samme header blir lest to ganger i samme fil. En funksjon som er definert i en header, må merkes inline, ellers får linkeren flere kopier av den og klager – det møter du i #6.

    RAII: konstruktøren henter, destruktøren rydder

    Hver OpenGL-ting du lager (buffer, VAO, shaderprogram) må slettes igjen. RAII betyr at du knytter dette til et objekts levetid: konstruktøren oppretter ressursen, destruktøren sletter den. C++ kaller destruktøren automatisk når objektet går ut av sitt scope (krøllparentesene det ble laget i), så du kan ikke glemme det.

    Lokale objekter dør i motsatt rekkefølge av den de ble laget i. Det sist laget dør først.

    Fella: konteksten må leve når destruktøren kjører

    En destruktør som sletter en OpenGL-ting, trenger en levende kontekst. Lager du objektene rett i main, dør de når main slutter – etter at glfwTerminate() har tatt konteksten. Det kan krasje, eller se helt fint ut på din maskin og krasje på en annen. Løsningen i issuene er et indre scope rundt objektene og loopen, som lukkes før glfwTerminate(). Se figuren under.

    Fella nummer to: ikke kopier eierne

    En VertexBuffer eier en buffer-id. Kopierer du objektet, finnes det to objekter med samme id – og når det første dør, sletter det bufferen som det andre fortsatt bruker. Resultatet er ingenting på skjermen og ingen feilmelding. Send derfor slike objekter som referanse (const VertexBuffer&), aldri som kopi. Vil du være helt sikker, kan C++ forby kopiering av en klasse helt – søk opp «deleted copy constructor».

    Hva VAO-en husker – og hva den ikke husker

    Dette er stedet der ting feiler stille. VAO-en husker attributtbeskrivelsene og hvilken indeksbuffer (EBO) som er bundet mens den er bundet. Den husker ikke hvilken vertex-buffer som er bundet – den informasjonen kopieres inn i hvert attributt i det øyeblikket du beskriver det. Konsekvensene:

    • Vertex-bufferen må være bundet når du beskriver attributtene, men kan løsnes etterpå.
    • Indeksbufferen må bindes mens VAO-en er bundet, og må ikke løsnes mens VAO-en fortsatt er bundet.

    Layouten regner for deg (#6)

    I modul 3 regnet du stride og offset for hånd. En BufferLayout er en liste over attributtene, og den regner ut det samme: stride er summen av størrelsene, og hvert attributts offset er summen av alle før det. Rekkefølgen i lista blir attributtnumrene 0, 1, 2 … – og de må stemme med layout(location = N) i shaderen. Bytter du rekkefølgen bare ett sted, leses posisjoner som farger, uten feilmelding.

    C++-verktøyene her er enum class (en navngitt liste av typer, som Float3), std::vector og std::initializer_list (som lar deg skrive lista med krøllparenteser).

    RenderCommands (#8): én trakt

    RenderCommands er et namespace, ikke en klasse, fordi det ikke har noe eget objekt å holde på – bare funksjoner. Når alle tegnekall går gjennom én funksjon, kan du telle dem. Antall tegnekall per frame er et av de viktigste målene på hvor tung en scene er; det får du bruk for når brettet har 64 ruter. Telleren ligger i et anonymt namespace i .cpp-fila, som betyr at ingen annen fil kan se den.

    Same picture, new owner

    In these five issues you learn no new graphics. You package the calls you wrote in #3 into classes, so the lab only uses them. That is called refactoring: the code changes, the behaviour does not. So the test after each issue is simple: does the picture look exactly as before?

    The payoff comes later. The game draws many things, and then you want to write «make a buffer with this data», not four OpenGL calls in the right order every time.

    A static library

    In #4, framework/ becomes a static library: a collection of compiled code that is glued straight into every program that uses it. The labs and the game link against it. When the CMake recipe marks the library's folder and dependencies PUBLIC, everything linking against the library inherits them automatically – which is why the lab finds VertexBuffer.h without you saying where it is.

    Header and source file

    Each class has a .h file that declares what the class can do (the promise) and a .cpp file that defines how (keeping it). Other files include only the header. #pragma once stops the same header being read twice in one file. A function defined in a header must be marked inline, or the linker gets several copies and complains – you meet this in #6.

    RAII: the constructor acquires, the destructor cleans up

    Every OpenGL thing you create (buffer, VAO, shader program) must be deleted again. RAII means tying this to an object's lifetime: the constructor creates the resource, the destructor deletes it. C++ calls the destructor automatically when the object leaves its scope (the braces it was created in), so you cannot forget.

    Local objects die in the reverse order of creation. The last one made dies first.

    The trap: the context must be alive when the destructor runs

    A destructor that deletes an OpenGL thing needs a live context. If you create the objects straight in main, they die when main ends – after glfwTerminate() has taken the context. It may crash, or look fine on your machine and crash on another. The issues' fix is an inner scope around the objects and the loop that closes before glfwTerminate(). See the figure below.

    Trap number two: do not copy the owners

    A VertexBuffer owns a buffer id. Copy the object and there are two objects with the same id – and when the first dies, it deletes the buffer the other still uses. The result is nothing on screen and no error. So pass these objects by reference (const VertexBuffer&), never by copy. To be completely safe, C++ can forbid copying a class altogether – look up «deleted copy constructor».

    What the VAO remembers – and what it does not

    This is where things fail silently. The VAO remembers the attribute descriptions and which index buffer (EBO) is bound while it is bound. It does not remember which vertex buffer is bound – that information is copied into each attribute at the moment you describe it. The consequences:

    • The vertex buffer must be bound when you describe the attributes, but may be unbound afterwards.
    • The index buffer must be bound while the VAO is bound, and must not be unbound while the VAO is still bound.

    Try all three variants in the state machine below.

    The layout does the arithmetic (#6)

    In module 3 you computed stride and offset by hand. A BufferLayout is a list of the attributes, and it computes the same thing: the stride is the sum of the sizes, and each attribute's offset is the sum of all before it. The order of the list becomes the attribute numbers 0, 1, 2 … – and they must match layout(location = N) in the shader. Change the order in only one place and positions are read as colours, with no error.

    The C++ tools here are enum class (a named list of types, like Float3), std::vector and std::initializer_list (which lets you write the list with braces).

    The Shader class (#7)

Hvilken side du ganger på, bestemmer aksen: på venstre side roterer kuben om verdens akser, på høyre side om sine egne. Det er samme regel som over – rekkefølgen er alt. Gjør modus 1 og 2; modus 3 (gimbal lock) er en øvelse du kan hoppe over hvis tiden er knapp.

        Order is everything

        Matrices act from right to left. In P · V · M · v, M happens first, then V, then P. The same goes inside the model matrix: «translate · rotate» means the shape is first rotated about its own centre and then moved. «Rotate · translate» means it is first moved and then rotated about the origin – it swings in an arc. Try both in the playground below.

        glm

        glm is the library that does the maths. Its types have the same names as in GLSL (vec3, mat4), so what you build in C++ can be sent straight to the shader. Angles are in radians: 90° is π/2. The most common mistake is passing degrees where radians are expected.

        Projection

        A perspective projection has four numbers: the field of view, the width/height ratio (aspect), and the near and far limits. The aspect number is what fixes the stretched square you saw in module 3. An orthographic projection has no perspective – things are the same size at any distance.

        Uniforms

        A uniform is a value in the shader that is the same for every corner in one draw call – for example the MVP matrix. You find it by name and upload the value from C++. The shader must be bound when you do. And again: misspell the name and nothing happens, with no error. #15 wraps this in Shader, the way module 4 wrapped the buffers.

        The depth buffer

        In 3D, surfaces overlap. The depth buffer stores, for each pixel, how near the nearest thing drawn there is. With the depth test on, the nearest wins regardless of order. The buffer must be cleared every frame, or old values remain and the picture smears. Without the depth test, draw order decides, and the cube looks inside out.

        Accumulating rotation (#16)

        In #16 you keep a matrix that «remembers» how the cube is turned, and multiply on a small rotation every frame while a key is held. Which side you multiply on decides the axis: on the left, the cube turns about the world's axes; on the right, about its own. Same rule as above – order is everything. Do modes 1 and 2; mode 3 (gimbal lock) is an exercise you can skip if time is short.

        Geometri i kode (#17)

        I stedet for å skrive tallene for hver figur for hånd, lager GeometricTools dem. To C++-verktøy er nye her. En template kan ta tall som parametere, slik at størrelsen på rutenettet er kjent når programmet kompileres. constexpr betyr at verdien kan regnes ut allerede ved kompilering. Resultatet ligger i et std::array, som har fast størrelse.

        Et rutenett er hjørner pluss en indeksliste: hver rute er to trekanter over sine fire hjørner. Issuet gir deg formlene. Tre ting å passe på:

        • Heltallsdivisjon. I C++ er 3 / 4 lik 0 når begge er heltall. Én av dem må være flyttall, ellers havner alle hjørnene på samme linje.
        • Samme omløpsretning. Alle trekantene skal gå samme vei rundt (mot klokka). Ellers forsvinner halvparten senere, når baksider skjules.

        Geometry in code (#17)

        Instead of typing the numbers for each shape by hand, GeometricTools generates them. Two C++ tools are new here. A template can take numbers as parameters, so the size of the grid is known when the program is compiled. constexpr means the value can be computed already at compile time. The result sits in a std::array, which has a fixed size.

        A grid is corners plus an index list: each cell is two triangles over its four corners. The issue gives you the formulas. Three things to watch:

        • Integer division. In C++, 3 / 4 is 0 when both are integers. One of them must be floating point, or all the corners land on the same line.
        • Same winding. All triangles must go the same way round (anticlockwise). Otherwise half of them vanish later, when back faces are hidden.
        • Look at the result as a wireframe. The issue shows how to draw only the edges. Then you see at once if a triangle is missing.

        The camera (#18)

The camera computes P · V in advance, so the lab needs just one matrix. The engine's camera always looks at the origin.

        Time (#20)

        According to the issue, this is the most common mistake in the whole course. Move something a fixed amount per frame and it goes twice as fast on a machine with twice as many frames. The fix is to measure how long has passed since the previous frame – delta time, dt – and multiply every speed by it. The speed then becomes «per second», which is the same everywhere. See the difference in the race below.

        The camera controller (#21, #26)

        Øvelser – i en annen verden enn oppgaven

        Exercises – in a different world from the assignment

        Hylla: En hylle går fra x = −1 til x = 1 og er delt i 4 like rom. Hvor er midten av hvert rom?

        Hvert rom er 0.5 bredt. Midtene: −0.75, −0.25, 0.25 og 0.75. Generelt: start + (nummer + 0.5) · bredde.

        Se på et sjakkbrett med (rad, kolonne) fra 0. Hva har alle rutene med samme farge til felles?

        Summen rad + kolonne er enten partall for alle, eller oddetall for alle.

        Klokka: Timene går 0–11. Hva er 10 + 3, og hva er 0 − 1, når klokka går rundt? Og hva gir -1 % 12 i C++?

        (10 + 3) går til 1. 0 − 1 skal bli 11. Men -1 % 12 er −1 i C++. Legg til 12 før du tar resten, så slipper du negative tall.

        Tastens tilstand over åtte frames er: oppe, oppe, nede, nede, nede, oppe, nede, oppe. Hvor mange frames er den nede, og hvor mange kanter er det?

        Nede i 4 frames. Kanter (oppe → nede): 2.

        Parkeringsroboten: En robot har en knapp. Har den tom gripeklo, løfter den bilen på plassen den står over. Holder den en bil, setter den den ned. Hvilke to situasjoner må den nekte, og hva bør den gjøre da?

        Nekte å løfte fra en tom plass, og nekte å sette ned på en opptatt plass. I begge tilfeller: ikke gjør noe, behold tilstanden som den er, og ikke krasj.

        Hvorfor er det lurt at brikkene er data (rute + lag) og ikke geometri?

        Da er reglene bare spørsmål om dataene («står det noe på denne ruta?»), og tegningen kan alltid lages på nytt fra dataene. Ingen ting må holdes i synk to steder.

        The shelf: A shelf runs from x = −1 to x = 1 and is split into 4 equal compartments. Where is the middle of each?

        Each compartment is 0.5 wide. The middles: −0.75, −0.25, 0.25 and 0.75. In general: start + (number + 0.5) · width.

        Look at a chessboard with (row, column) from 0. What do all squares of the same colour have in common?

        The sum row + column is either even for all of them, or odd for all of them.

        The clock: Hours run 0–11. What is 10 + 3, and what is 0 − 1, when the clock wraps around? And what does -1 % 12 give in C++?

        (10 + 3) wraps to 1. 0 − 1 should become 11. But -1 % 12 is −1 in C++. Add 12 before taking the remainder, and you avoid negative numbers.

        A key's state over eight frames is: up, up, down, down, down, up, down, up. How many frames is it down, and how many edges are there?

        Down for 4 frames. Edges (up → down): 2.

        The parking robot: A robot has one button. With an empty claw it lifts the car in the space below it. Holding a car, it puts it down. Which two situations must it refuse, and what should it do then?

        Refuse to lift from an empty space, and refuse to put down on an occupied space. In both cases: do nothing, keep the state as it is, and do not crash.

        Why is it wise for the pieces to be data (tile + team) and not geometry?

        Then the rules are just questions about the data («is something on this tile?»), and the drawing can always be rebuilt from the data. Nothing has to be kept in sync in two places.

        Sjekk deg selv

        Check yourself

        Hva er forskjellen på «tasten er nede» og «tasten ble trykket», og hvilken trenger markøren?

        Nede er en tilstand som varer i mange frames. Trykket er overgangen fra oppe til nede, som skjer i én frame. Markøren og plukk-tasten trenger overgangen.

        Hvorfor binder du kameraet til WASD og ikke piltastene?

        Piltastene brukes av markøren. Leser to ting de samme tastene, slåss de.

        Hvorfor trengs dybdetesten først når brikkene kommer?

        Brettet er flatt, men kubene overlapper hverandre og står oppå brettet. Uten dybdetest bestemmer tegnerekkefølgen hva som synes.

        Hva betyr «ingen rå gl i assignment/» når du trenger noe nytt?

        At du legger det nye inn i motoren (framework/) og bruker det derfra.

        What is the difference between «the key is down» and «the key was pressed», and which does the selector need?

        Down is a state that lasts many frames. Pressed is the transition from up to down, which happens in one frame. The selector and the pick-up key need the transition.

        Why bind the camera to WASD and not the arrow keys?

        The arrow keys are used by the selector. If two things read the same keys, they fight.

        Why is the depth test needed only once the pieces arrive?

        The board is flat, but the cubes overlap each other and stand on the board. Without the depth test, draw order decides what is visible.

        What does «no raw gl in assignment/» mean when you need something new?

        That you add the new thing to the engine (framework/) and use it from there.
